# studed — 서비스 기획서 (원본)

> 이 문서는 서비스 기획 확정본이다. 개발 중 애매하거나 이 문서와 충돌하는 부분이
> 있으면, 임의로 넘어가지 말고 사용자에게 먼저 질문한다.

## 0. 한눈에 보는 요약

**studed**는 고등학생이 수행평가 안내문 사진을 올리면, 산출물 종류(글로 그대로 제출 가능한 것 / 외부 툴로 제작해야 하는 것)를 자동 판별해서 **완성된 원고** 또는 **실행 계획**을 실제 검색 출처와 함께 만들어주는 서비스입니다.

핵심 차별점은 한 줄로 요약하면: **"남들과 겹치지 않는, 사람이 쓴 것 같은, 출처 있는 수행평가 AI"**

- 1순위 차별점: 전국 단위로 학생들의 결과물이 소수로 쏠리지 않도록 임베딩(텍스트를 숫자로 변환해 의미상 유사도를 비교하는 방식) 기반으로 자동 다양화
- 보조 장치: 결과물이 AI 특유의 문체 없이 자연스럽게 읽힘, 지어낸 출처가 아닌 실시간 검색 기반 실제 출처 제공

백엔드는 Gemini API(이미지분석/검색그라운딩/생성/임베딩) + Postgres/pgvector 조합, 프론트는 노션+유니브AI 스타일의 좌측 사이드바 구조입니다.

## 1. 문제 정의 & 타겟 유저

**타겟 유저**: 전체 고등학생 (학년·계열 제한 없음)

**문제 인식** (두 가지를 동등한 비중으로 해결):
1. 학생 대부분(고등학생 기준 86%가 생성형 AI 사용 경험, ChatGPT 압도적 1위)이 수행평가에 범용 AI를 그대로 씀 → 상투적 표현("다양한 관점에서" 등)과 뻔한 소재로 결과가 겹침. 실제 사례: 한 학교 영어 신조어 수행평가에서 학생 80%가 "스몸비(스마트폰+좀비)"로 답이 몰림
2. AI가 출처를 지어내는(할루시네이션) 문제

**왜 지금인가**: 고등학생의 생성형 AI 사용률이 이미 86%로 매우 높아서, "AI를 쓰느냐 마느냐"가 아니라 "어떻게 하면 겹치지 않고 신뢰할 수 있게 쓰게 하느냐"가 실질적인 문제가 된 상황

## 2. 핵심 가치제안

범용 AI 챗봇 대비 studed의 차별점:

| 항목 | 범용 AI (ChatGPT 등) | studed |
|---|---|---|
| 소재 쏠림 방지 | 없음 (같은 질문엔 비슷한 답) | 전국 단위 자동 분산 |
| AI 문체 티 | 남 (번역투, 상투어 등) | 별도 규칙으로 제거 시도 |
| 출처 신뢰성 | 종종 지어냄 | 실시간 검색 + 링크 유효성 검증 |
| 산출물 형태 판별 | 사용자가 직접 프롬프트 설계해야 함 | 안내문 사진만 올리면 자동 분류(완성원고 vs 실행계획) |

**한 줄 포지셔닝**: 차별점 있는 수행평가 자동화 AI — 자동화는 기본값, "남들과 겹치지 않는다"는 것이 1순위 메시지

### 포지셔닝 상세

과제가 요구하는 산출물 요소별로 자동 분기:
- **AI가 만든 텍스트를 그대로 제출 가능한 요소** (독서록, 감상문, 추천 이유 서술, 발표 대본 등) → **완성된 원고**를 직접 생성
- **외부 툴/물리적 제작이 추가로 필요한 요소** (PPT/포스터 디자인, 물리적 제작물 등) → **실행 계획**을 생성 (예: PPT는 슬라이드별 구성안을 계획서로 제공해 감마·캔바 등에 붙여넣게 함)
- 한 과제 안에 두 요소가 섞여 있으면(예: "PPT + 대본") 각각 계획서/완성 원고로 나눠서 함께 출력
- 온라인 산출물(포스터/PPT 파일 자체)은 만들지 않음
- 완성 원고에서도 시/소설처럼 저작권 있는 원문은 재현하지 않고 출처 안내로 대체 (5-2 참고)

## 5. AI 모델 선택

### 5-0. 처리 파이프라인 개요

```
[1단계: 안내문 파싱]      [2단계: 클러스터 식별/회피 지시 계산]      [3단계: 검색+생성]                [4단계: 후처리]
 Gemini Flash-Lite    →     PostgreSQL pgvector              →   Gemini Flash (Search Grounding)  →  (분기)
 - 행정/핵심 필드 분리          - 과제 임베딩 계산 → 클러스터 매칭         - 회피 지시 반영해 원고/계획서 생성      완성 원고 → 마크다운 그대로 스트리밍
 - 텍스트제출형/외부제작형 분류    - 3개월 롤링+스무딩으로 회피 지시 산출                                         (JSON 변환 불필요)
                                                                                                  계획서 → 2차 JSON 구조화 변환 필요
```

**핵심은 순서**: 클러스터 식별과 회피 지시 계산(2단계)이 반드시 생성(3단계)보다 **먼저** 일어나야, 그 회피 지시를 3단계 프롬프트에 실제로 반영할 수 있음. 4단계는 산출물 형태에 따라 분기 — 완성 원고는 여기서 끝나고, 계획서만 JSON 변환을 한 번 더 거침 (5-1 참고). 생성된 결과물(4단계 산출물)의 임베딩은 별도로 계산해 `task_embeddings`에 저장하고, 다음 요청들의 6-2 비율 계산에 쓰임 (6-0, 10번 참고 — 2단계에서 쓰는 "과제 임베딩"과는 다른 값).

### 역할별 모델 조합

전부 Gemini로 통일 (역할별 모델 조합)

| 단계 | 모델 | 이유 |
|---|---|---|
| 이미지 분석 + 구조화 스키마 파싱 + 산출물 요소 분류 | Gemini Flash-Lite 계열 | 최저가, 이미지 인식 가능 |
| 검색 + 원고/계획서 생성 (핵심) | Gemini Flash 계열 (Google Search 그라운딩) | 검색 그라운딩 네이티브 지원 |
| 소재 풀 생성/확장 (언어유희형 과제용) | Gemini Flash-Lite 계열 | 저비용, 필요시 재생성 |
| 동일 과제 클러스터링 경계 케이스 판별 | Gemini Flash-Lite 계열 | 애매한 구간만 확인용 호출 |
| 임베딩 생성 (클러스터 매칭용 "과제 임베딩", 겹침방지·MMR용 "결과물 임베딩" 둘 다) | Gemini Embedding 모델 | pgvector와 바로 연동. **개발 착수 시 정확한 모델명·차원 수를 Google 공식 문서에서 확인하고 pgvector 컬럼 차원을 그에 맞춰 설정할 것** |

> **모델명/가격은 실제 개발 착수 직전에 Google 공식 문서에서 재확인할 것** (버전 교체가 빠른 영역이라 이 문서의 모델명이 개발 시점엔 구버전일 수 있음). 품질 부족 시 "검색+생성" 단계만 Claude Haiku 계열로 교체 가능하도록 독립 모듈로 개발.

**주의**: 개발 도구(Claude Code)와 서비스 런타임 API(Gemini)는 완전히 별개.

### 5-1. 검색 그라운딩 파이프라인 — 산출물 형태별 분기

- **완성 원고 (독서록·감상문 등)**: 그라운딩 켠 상태로 마크다운 그대로 스트리밍 출력. 별도 JSON 변환 불필요 → 체감 대기시간 3~4초대 목표
- **실행 계획 (PPT 구성안 등, JSON 구조화 필수)**: 1차 텍스트+인용 호출 → 2차 JSON 변환 호출의 2단계 파이프라인 유지 (한 번에 처리하면 인용 메타데이터 소실 위험) → 레이턴시 8~12초 가능성, MVP 1단계에서 최우선 실측 후 스트리밍/단계별 로딩 문구("관련 출처 검색 중...", "겹침 없는 원고 구성 중...") 적용 여부 결정
- 두 경로 모두 생성 후 **출처 링크 HTTP 상태 체크(유효성 검증)** 적용

**환각 대비**: 완성 원고가 구체적 사실(책 줄거리 등)에 의존하는 경우, 검색 결과가 충분하지 않으면 생성하지 않고 "자료가 부족해 정확한 생성이 어렵다"고 안내(F13). 정상 생성되더라도 상단 핵심 요약 3줄 블록으로 학생이 스스로 검증할 수 있는 지점을 제공.

### 5-2. 저작권 있는 원문(시/소설/뉴스 인용문 등) 처리 원칙

- 원문을 본문에 그대로 인용하지 않고, 출처 링크 제공 + 학생이 직접 원문을 찾아 읽도록 유도
- 완성 원고 생성 시에도 구체적 문장을 베끼지 않고 검색 정보를 바탕으로 파라프레이징

### 5-3. AI 말투 방지 지침 (필수 — 생성 프롬프트에 반드시 포함)

완성 원고와 계획서 모두 "AI가 쓴 티"가 나지 않아야 함. 검색+생성 단계(Gemini Flash) 시스템 프롬프트에 아래 규칙을 명시적으로 포함시킬 것:

**피해야 할 패턴**
- 번역투: "~를 통해", "~에 대해", "~에 있어서", 이중 피동("~되어진다"), "가지고 있다" 남용
- 기계적 구조: "첫째/둘째/셋째" 같은 형식적 나열, 과도한 불릿·헤딩·이모지, 콜론(:) 부제 헤딩 공식("X: Y" 패턴) 남발
- AI 특유 관용구: "결론적으로", "시사하는 바가 크다", "주목할 만하다", "혁신적인", "다양한 관점에서" 같은 상투어
- 과도한 hedging: "~할 수 있을 것으로 보인다"처럼 여러 겹으로 완곡하게 돌려 말하기
- 문두 접속사 남발: "또한/따라서/즉/나아가"로 문장을 계속 시작
- 형식명사 과다: "것이다", "점", "수", "바" 남용
- 수식어 중복: "매우", "정말" 같은 강조어 이중 사용, "~적/~성/~화" 접미사 남발

**대신 이렇게 쓸 것**
- 문장 길이에 변화를 주고, 종결어미를 반복하지 않기
- 학생 본인의 목소리처럼, 구체적 근거·경험·판단이 자연스럽게 드러나게 쓰기
- 사실·수치·고유명사·인용은 그대로 유지하되, 문체만 자연스럽게

## 6. 겹침 방지 / 차별화 시스템

### 핵심 원칙: "겹침 방지"가 아니라 "확률 쏠림 방지"

### 6-0. 동일 과제 클러스터 식별

1. 이미지 분석 단계에서 구조화 출력을 강제해 `administrative_info`(제출기한·감점기준 등)와 `core_task_info`(핵심주제·요구사항·수행방식)를 물리적으로 분리 추출.
2. `core_task_info` 값만 결합해 **"과제 임베딩"**(클러스터 매칭 전용)을 계산 — **이 값은 판정 순간에만 쓰고 DB에 영구 저장하지 않음**
3. 방금 계산한 과제 임베딩을 pgvector 코사인 유사도로 **기존 클러스터의 대표 벡터(`clusters.centroid_vector`)와 비교**, 애매한 경계 구간만 LLM 확인
4. 매칭된 클러스터가 있으면 `centroid_vector`를 이동평균으로 갱신, 없으면 새 클러스터를 생성

> **핵심 주의 — 두 임베딩을 절대 섞지 말 것**: `clusters.centroid_vector`는 안내문(`core_task_info`)의 임베딩들로만 구성·갱신됨. `task_embeddings.content_embedding`과는 절대 같은 값이 아니고 섞이면 안 됨.

### 6-1. 언어유희형 과제 — 구조적 강제 + 동적 확장 (MVP 이후)

### 6-2. 비율 기반 억제 + 3개월 롤링 윈도우

- 클러스터 내 유사 산출물 비율이 임계 기준을 넘으면 회피 지시 강하게 발동. 절대 개수 기준 안 씀
- 3개월 롤링 윈도우, 라플라스 스무딩 (K=20~30)
- 비교 대상: `task_embeddings.content_embedding` (결과물 임베딩)
- 분모("전체건수")는 캐시 컬럼 없이 실시간 COUNT

**재생성 시 버전 처리**: 새 버전 추가 시 이전 버전은 `is_current=false`. 최신 버전만 비율 계산에 포함. 재생성 직전 비교에서는 자기 자신의 `submission_id` 제외.

### 6-3. 추가 다양성 확보 장치 (MVP 이후 고도화)

우선순위: 회피 지시 명시 > 입력 다양화(지침+개인화+검색) > 다중생성 후 MMR 선별 > 구조 가변화 > temperature 조절

## 7. 교과서 관련 — 저작권 이슈로 스코프 제외

교과서 원문을 학습시키거나 벡터DB에 저장하지 않음. 성취기준(공공저작물)은 자유 활용 가능.

## 8. 뺀 기능들

루브릭 매핑/예상 점수, 독창성 지표(%) 노출, 일정 리마인더, 교과서 원문/스타일 참고.

## 9. 부가 기능

### 9-4. 결과물 출력 포맷

**계획서**: `[오늘 당장 할 일(예상 소요시간)] + [검색할 키워드] + [참고 출처 링크]`

**완성 원고**: 상단 핵심 요약 3줄 + 문장마다 출처 각주, 마크다운.

### 9-5. 수정(재생성) 기능

하루 1회, 자유 텍스트로 수정 방향 입력. `task_embeddings`는 새 레코드 추가 + 버전관리.

## 10. 데이터베이스 스키마

`user_histories`(개인정보 O), `task_embeddings`(개인정보 X, FK 없음), `clusters`.
자세한 컬럼 정의는 `supabase/migrations/0001_init.sql` 참고 — 원본 기획 의도의 주석이
그대로 달려 있음.

핵심 원칙: `user_histories`와 `task_embeddings` 사이에 FK 없음. 개인식별정보는
`task_embeddings`, `clusters` 어느 테이블에도 저장하지 않음. 단, 두 테이블 모두
`submission_id`를 공유하므로 값 매칭을 통한 잔여 재식별 리스크는 인지하고 진행.
